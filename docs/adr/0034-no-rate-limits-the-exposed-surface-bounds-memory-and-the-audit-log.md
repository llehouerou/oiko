# No rate limits: the exposed surface bounds memory and the Audit log

_Amended by [ADR 0037](0037-a-live-view-is-fragmented-mp4-in-the-answer-to-a-post.md): the Content Security Policy also allows `media-src 'self' blob:`, and the Permissions Policy allows `autoplay=(self)`._

Oiko is exposed to the internet behind a reverse proxy that may add nothing but TLS, so every client arrives from the proxy's address and no forwarded header is trusted (ADR 0027). A limit keyed on the client's address is then one bucket for the whole internet, which a scanner fills to lock the household out. It would also protect nothing: every secret Oiko accepts (a Sign-in link, a Setup link, a Token, a Kiosk pairing, a Session) carries at least 128 random bits and there is no password (ADR 0024), so guessing is hopeless however many attempts are made. Oiko therefore limits no request rate. It bounds instead what an anonymous request can make it hold, in memory and in the Audit log (ADR 0033), and leaves volumetric floods to the reverse proxy, which the documentation says.

## Considered Options

- **Per-address limits with an opt-in trusted-proxy setting**: limits that track real clients when the proxy is configured exactly right, but more configuration and header parsing, a global bucket by default, and nothing that 128-bit secrets do not already protect.
- **One global limit on refused credentials**: simple, but any scanner then locks out the household and its Programs.
- **Leaving everything to the proxy**: nothing to build, but Oiko must stay safe when the proxy adds only TLS.
- **Refusing new ceremonies or pairings when the cap is reached**: a modest flood would block every sign-in until entries expire, while dropping the oldest only hurts a ceremony that has lived longer than the flood needs to replace 10,000 entries.
- **Recording every refusal, as ADR 0033 first said**: a scanner sending bogus Tokens at 100 requests a second would write about 3 billion entries a year.
- **A Content Security Policy in Report-Only first**: a softer rollout, but it needs a public endpoint accepting anonymous reports, and a release in which nothing is enforced.
- **A Host allow-list, or a fetch-metadata policy on `/api`**: the usual defences against DNS rebinding and cross-site reads, but the network never authenticates (ADR 0027), so a rebound page carries no credential, Programs call Oiko by its LAN address (ADR 0028), and a `SameSite=Strict` cookie is already absent from cross-site requests.

## Consequences

- **Memory.** WebAuthn ceremonies (5 minutes, ADR 0032) and Kiosk pairing requests (10 minutes, ADR 0029) are capped at 10,000 each; when a cap is reached, the oldest entry is dropped and the new one accepted. The HTTP server sets a 10 s `ReadHeaderTimeout`, a 30 s `ReadTimeout`, a 120 s `IdleTimeout` and 64 KiB `MaxHeaderBytes`. It has no global `WriteTimeout`: the event stream sets a 30 s deadline on each write instead. Request bodies stay capped at 64 KiB.
- **Audit log.** A refusal where no identity is found (an invalid Token, an unknown or ended Sign-in link or Setup link, an unknown Passkey, an anonymous pairing request that expired) is recorded individually up to 100 an hour, all kinds together; past that, one entry an hour for each kind of event carries the count. A refusal tied to a known identity (a signature counter regression, a failed step-up, a pairing an Admin refused) is always recorded individually. At worst about a million entries a year.
- **Headers.** Every response carries `Content-Security-Policy: default-src 'self'; script-src 'self'; style-src 'self'; img-src 'self'; font-src 'self'; connect-src 'self'; object-src 'none'; base-uri 'none'; form-action 'self'; frame-ancestors 'none'`, enforced from the first release and checked by a browser test against the built client; the build inlines no asset as a `data:` URL. Also `X-Content-Type-Options: nosniff`, `Referrer-Policy: no-referrer`, `Cross-Origin-Opener-Policy: same-origin`, `Cross-Origin-Resource-Policy: same-origin`, a `Permissions-Policy` that denies every feature except `web-share` and `clipboard-write` for Oiko itself (sharing a Sign-in link, ADR 0030), and `Strict-Transport-Security: max-age=31536000`, without `includeSubDomains` or `preload` since the public host may share its domain with sites Oiko knows nothing of. Browsers ignore HSTS over plain HTTP, so it costs nothing on `localhost`. No `X-Frame-Options`, no CORS header, no `Clear-Site-Data`: the client stores only display preferences.
- **Cookies.** The Session cookie (ADR 0025) and the Kiosk's claim cookie (ADR 0029) are `SameSite=Strict`. The web client's HTML needs no Session and every data request is a same-origin fetch, so a Person arriving through a link from another site still lands signed in.
- **Cross-origin requests.** `http.CrossOriginProtection` guards every mutation, with the public URL added as a trusted origin so a browser without `Sec-Fetch-Site` behind a proxy that rewrites `Host` is not refused. Nothing changes state on a GET.
- **Caching.** Files under `/assets/`, named by their content hash, are `public, max-age=31536000, immutable`. `index.html` and the other top-level files are `no-cache`, with an ETag computed at start from the embedded content, since embedded files carry no modification time; an upgrade shows at once. Every `/api/` response is `no-store`. The web client is served to anyone, signed in or not: the repository is public and the sign-in page is part of it.
