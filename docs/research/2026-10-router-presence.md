# Research: how can a router tell which phones are on the network?

## Summary
A router can expose three different, non-equivalent signals — Wi-Fi association (the radio driver's station table), the ARP/neighbor cache, and DHCP leases — and each has a different latency and failure mode. DD-WRT exposes all three through SSH (`wl`/`wlanconfig`/`iw`, `/proc/net/arp`, `dnsmasq.leases`) and through an HTTP status page (`Status_Wireless.live.asp` / `Status_Lan.live.asp`, HTTP Basic Auth, polled — this is exactly what Home Assistant's `ddwrt` integration does). No single generic protocol works across DD-WRT, OpenWrt, UniFi, and Fritz!Box — each needs its own adapter, though SSH+`iw`/`ubus` is close to a common denominator on Linux-based firmwares. Phone-side behavior (Wi-Fi power save, MAC randomization per network on iOS 18+ and Android 10+) means a phone can look "away" for anywhere from seconds to tens of minutes depending on method, and MAC address is the only usable device key — hostname and IP are unreliable for identification.

## Findings

### DD-WRT interfaces

1. **Claim:** DD-WRT's SSH shell exposes wireless-association data via hardware-specific tools: `wl assoclist` (and `wl -i <ifname> assoclist`) for Broadcom radios, `wl_atheros assoclist` / `wlanconfig ath0 list sta` for legacy Atheros radios, and `iw dev <iface> station dump` for mac80211-based (modern Atheros/Qualcomm/ath9k/ath10k) drivers. There is no single command that works on all DD-WRT builds; the correct tool depends on the chipset/driver the specific build was compiled for.
   **Sources:** [DD-WRT forum — WL IS NEUTERED](https://forum.dd-wrt.com/phpB2/viewtopic.php?p=1265504), [DD-WRT forum — Atheros/Broadcom command table](https://forum.dd-wrt.com/phpBB2/viewtopic.php?t=286300), [OpenWrt forum archive — wl/wlanconfig/iw comparison](https://forum.archive.openwrt.org/viewtopic.php?id=27581), [Super User — DD-WRT wl assoclist](https://superuser.com/questions/1198345/dd-wrt-how-can-i-guess-via-cli-shell-the-link-quality-of-each-wifi-associated-c).
   **Support:** direct evidence (forum posts quoting command tables and real router output across R7000/WAC124/Archer hardware). **Confidence:** high.

2. **Claim:** `wl`/`wlanconfig`/`iw` report Wi-Fi **association** only — a device that is radio-associated to the AP but has gone idle/asleep stays in this list only as long as the driver keeps it associated (no 802.11 deauth). This is a narrower and generally faster signal than ARP or DHCP: it reflects "attached to this radio right now," not "has recently exchanged IP traffic."
   **Sources:** interpretation from the command outputs and DD-WRT wiki (`Status_Wireless.live.asp` "active_wireless" field), cross-checked against the `iw station dump` fields (signal, inactive time, connected time) documented in [OpenWrt wireless utilities docs](https://openwrt.org/docs/guide-user/network/wifi/wireless-tool/wireless.utilities).
   **Support:** interpretation. **Confidence:** medium-high.

3. **Claim:** `/proc/net/arp` (readable via SSH `cat /proc/net/arp`) and DD-WRT's DHCP lease file (dnsmasq `leases`, surfaced in the UI/status page as `dhcp_leases`) give a second, independent view: ARP shows which IPs have recently resolved to a MAC on the LAN segment (regardless of Wi-Fi vs. wired), and DHCP leases show which MAC/IP/hostname bindings the router has handed out, with a lease expiry — not real-time presence.
   **Sources:** [Home Assistant `ddwrt` device_tracker.py source](https://github.com/home-assistant/core/blob/dev/homeassistant/components/ddwrt/device_tracker.py) (parses `arp_table` and `dhcp_leases` fields from the live status pages).
   **Support:** direct evidence (source code field names and parsing logic). **Confidence:** high.

4. **Claim:** DD-WRT's `Info.live.htm` / `Status_Wireless.live.asp` / `Status_Lan.live.asp` are AJAX-polled HTTP endpoints returning a flat `{field::value}` text format (not JSON); they are protected by the router's normal admin HTTP Basic Auth (the same username/password as the web UI), served over plain HTTP by default unless the admin explicitly enables HTTPS-only administration. The `active_wireless` field in `Status_Wireless.live.asp` is the exact server-side source for the "Wireless Nodes" table; an older information-disclosure advisory shows `Info.live.htm` returning the same style of data, in some builds without requiring authentication for that specific endpoint.
   **Sources:** [DD-WRT source — Status_Wireless.live.asp](https://github.com/mirror/dd-wrt/blob/master/src/router/kromo/dd-wrt/Status_Wireless.live.asp), [Packet Storm — DD-WRT info disclosure advisory](https://dl.packetstormsecurity.net/1012-exploits/dd-wrt_info_disclosure.pdf), [Home Assistant ddwrt source](https://github.com/home-assistant/core/blob/dev/homeassistant/components/ddwrt/device_tracker.py) (uses `requests.get(url, auth=(username,password))`, HTTP by default, `verify_ssl` optional when HTTPS is used).
   **Support:** direct evidence for HA's auth mechanism; the historical no-auth disclosure is from an older, specific advisory and should not be assumed to generalize to current builds. **Confidence:** medium (auth mechanism: high; universality of the old disclosure: low).

5. **Claim:** Home Assistant's legacy `ddwrt` device_tracker polls `Status_Wireless.live.asp` by default (`wireless_only: true`) — reading the `active_wireless` field and keeping only tokens that match a MAC-address regex — or `Status_Lan.live.asp` reading `arp_table` when `wireless_only: false`. It resolves names separately by parsing the `dhcp_leases` field (5-field CSV groups: name, ?, MAC, IP, ?) into a MAC→name map, fetched lazily on first `get_device_name` call. It uses a 4-second HTTP timeout per poll and treats HTTP 401 as an auth failure (logged, scan treated as failed) rather than retried with backoff.
   **Sources:** [Home Assistant `ddwrt/device_tracker.py`](https://github.com/home-assistant/core/blob/dev/homeassistant/components/ddwrt/device_tracker.py).
   **Support:** direct evidence (full source read). **Confidence:** high.

6. **Claim:** DD-WRT differs materially between Broadcom and Atheros/Qualcomm (and newer mac80211-based) builds, not just in command names but in what "wireless-only" visibility is reachable from HTTP: `Status_Wireless.live.asp`'s `active_wireless` field is generated router-side from whichever association API that build's driver supports, so coverage of the HTTP method inherits the same hardware fragmentation as the CLI tools.
   **Sources:** [DD-WRT source](https://github.com/mirror/dd-wrt/blob/master/src/router/kromo/dd-wrt/Status_Wireless.live.asp) + command-table evidence above.
   **Support:** researcher inference (combining two separately-confirmed facts: driver fragmentation at the CLI level, and the HTTP page being driver-sourced). Not directly stated by a single source. **Confidence:** medium.

7. **Claim:** SNMP is also offered by DD-WRT (SNMP daemon toggle in Administration → Management) but was not found, in this pass, to expose a documented, reliably-populated wireless-association MIB on all builds; community reports treat SNMP mainly for traffic/interface counters rather than per-client association. Not independently confirmed with a primary source for wireless client listing via SNMP.
   **Support:** missing evidence / unresolved. **Confidence:** low — flagged as a gap, not a claim.

### Generic, router-agnostic alternatives

8. **Claim:** ARP cache reading and ping/ARP-ping sweeps from Oiko's own host do not need router API access and work against any router, but they conflate the **network's** state with the **host OS's** ARP table timeout, and they depend on the target responding to layer-2/3 probes, which many phones suppress or delay while radio-sleeping.
   **Sources:** interpretation of [Home Assistant Nmap Tracker docs](https://www.home-assistant.io/integrations/nmap_tracker/) ("modern smart phones will usually turn off WiFi when they are idle. Simple trackers like this may not be reliable on their own.") and the HA community thread on tracker instability.
   **Support:** direct evidence (official HA docs explicitly warn about this) + interpretation. **Confidence:** high.

9. **Claim:** Nmap-based presence detection (as used by HA's `nmap_tracker`) is widely reported as noisy/"flapping" for phones specifically; HA's own GitHub issue tracker documents an upstream Nmap bug where ARP scanning misses alive Android hosts under some conditions, and a merged HA PR switched defaults to `-sn -PR -n` (ARP ping, no port scan, no DNS) specifically to reduce false negatives/slowness, which still did not eliminate flapping reports in the community.
   **Sources:** [nmap/nmap#92 — ARP scan misses alive hosts](https://github.com/nmap/nmap/issues/92), [HA PR #153047 — nmap_tracker default options](https://github.com/home-assistant/core/pull/153047), [HA PR #67708 — earlier default-options tuning](https://github.com/home-assistant/core/pull/67708), [HA community — "Nmap device scanner unstable device state"](https://community.home-assistant.io/t/nmap-device-scanner-unstable-device-state/222015).
   **Support:** direct evidence. **Confidence:** high.

10. **Claim:** OpenWrt exposes Wi-Fi association over `ubus call iwinfo assoclist '{"device":"wlan0"}'` (requires the `rpcd-mod-iwinfo` package), giving MAC, signal, average signal, noise, inactivity time, connection time, and auth state per station — structurally similar in content to DD-WRT's `wl`/`iw` output but delivered as structured JSON over `ubus`, reachable remotely via `ubus`-over-SSH or the `rpcd` JSON-RPC HTTP endpoint used by LuCI.
    **Sources:** [OpenWrt wiki — ubus iwinfo](https://openwrt.org/docs/guide-developer/ubus/iwinfo), [openwrt/rpcd iwinfo.c](https://github.com/openwrt/rpcd/blob/master/iwinfo.c).
    **Support:** direct evidence. **Confidence:** high.

11. **Claim:** UniFi's official local Network API exposes `GET /v1/sites/{siteId}/clients` ("List Connected Clients") returning currently-connected client records (MAC, connection type, etc.); it is poll/request based with no documented presence-change webhook, so a consumer must poll and diff to derive arrival/departure events itself.
    **Sources:** [Ubiquiti Help Center — Getting Started with the Official UniFi API](https://help.ui.com/hc/en-us/articles/30076656117655-Getting-Started-with-the-Official-UniFi-API), [UniFi Network API developer reference](https://developer.ui.com/network/v10.0.162).
    **Support:** direct evidence. **Confidence:** high.

12. **Claim:** AVM Fritz!Box exposes host/presence data via the **TR-064** SOAP API, service `urn:dslforum-org:service:Hosts:1`, actions `GetHostNumberOfEntries`, `GetGenericHostEntry`/`GetSpecificHostEntry`, and AVM's own extension `X_AVM-DE_GetHostListPath` (a single URL returning all hosts as XML, with fields including MAC, IP, `active` boolean, interface, and name) — a DHCP/ARP-table-style view, not a raw Wi-Fi-association table, authenticated via TR-064's own HTTP digest/SOAP auth scheme.
    **Sources:** [AVM — TR-064 Hosts service reference (PDF)](https://fritz.support/resources/TR-064_Hosts.pdf), [AVM — hostsSCPD.pdf official service description](https://avm.de/fileadmin/user_upload/Global/Service/Schnittstellen/hostsSCPD.pdf), community client libraries confirming the `Host{mac,ip,active,name,interface}` shape (e.g. [lukesthl/fritzbox](https://github.com/lukesthl/fritzbox)).
    **Support:** direct evidence for the API shape (official AVM PDF); the `active` field's exact definition (association vs ARP/DHCP-derived) was not confirmed from primary AVM documentation in this pass. **Confidence:** medium.

13. **Claim:** Because each firmware family (DD-WRT, OpenWrt, UniFi, Fritz!Box) exposes a different transport (HTTP Basic-Auth live-status pages / SSH text; `ubus` JSON-RPC; REST+API-key; TR-064 SOAP) and a different native concept of "connected" (association vs. ARP/DHCP-derived host record), one generic Bridge cannot cover all of them with a single protocol client. A practical architecture needs one adapter per firmware family, but SSH + a Linux-tool-based parser (`iw`/`wl`-family output, `/proc/net/arp`, dnsmasq leases) is the closest common denominator across DD-WRT and OpenWrt specifically, since both are Linux-based and reachable over SSH.
    **Support:** researcher inference drawn from findings 1–12, not asserted by any single source. **Confidence:** medium.

### Phone-side behavior

14. **Claim:** Apple's current (iOS 18 / iPadOS 18 / macOS 15 / watchOS 11 / visionOS 2 and later) Wi-Fi privacy model offers three per-network modes: **Off** (hardware MAC, trackable), **Fixed** (one private address per network, the default for secure networks like WPA2-Personal/Enterprise), and a newer **Rotate Wi-Fi Address** opt-in mode that changes the address "at random times" while connected to that network to reduce tracking even within one network.
    **Sources:** [Apple Support — Use private Wi-Fi addresses on Apple devices](https://support.apple.com/en-us/102509), [Apple Platform Security guide — Wi-Fi privacy with Apple devices](https://support.apple.com/guide/security/wi-fi-privacy-with-apple-devices-sec31e483abf/web), [MacRumors — iOS 18 Rotate Wi-Fi Address](https://www.macrumors.com/2024/06/10/ios-18-rotate-wifi-address/) (secondary, used only for corroboration/date context).
    **Support:** direct evidence (Apple's own docs). **Confidence:** high.

15. **Claim:** On Android 10+, Wi-Fi MAC randomization is on by default per-network and uses **persistent randomization** (one stable randomized MAC per SSID/security-type/FQDN, unchanged until factory reset) in Android 10–11. Starting in Android 12, some networks instead get **non-persistent randomization**, re-randomizing the MAC at the start of a new connection when either (a) the DHCP lease has expired *and* >4 hours have passed since last disconnect, or (b) the current randomized MAC for that network is >24 hours old; a developer option can force non-persistent randomization globally.
    **Sources:** [Android Open Source Project — MAC randomization behavior](https://source.android.com/docs/core/connect/wifi-mac-randomization-behavior).
    **Support:** direct evidence (AOSP official docs). **Confidence:** high.

16. **Claim:** For Oiko's purposes this means: on a *given* home Wi-Fi network, a phone's MAC address is normally stable for long periods (fixed/persistent randomization is the default on both platforms for a known, secured home network), but it is **not the device's real hardware MAC** and is **different from the MAC the same phone uses on any other network** — and on iOS 18+ or non-persistent-randomization Android 12+ conditions, the MAC used on the *same* home network can itself change after roughly a day or after a DHCP-lease-expiry-plus-4-hours condition, or at Apple's unspecified "random times" if the user opts into Rotate Wi-Fi Address.
    **Support:** researcher inference combining findings 14–15. **Confidence:** medium — the stable-on-known-network default is well supported; the edge cases (rotation, non-persistent) are real but not universal, and their practical frequency for a typical home network was not measured in any primary source found.

17. **Claim:** iOS does not publish a single universal "disconnect after N minutes of idle" rule for Wi-Fi itself; the only concretely documented timing in Apple's developer docs is at the **app** level: a foreground app that does not request persistent Wi-Fi (`UIRequiresPersistentWiFi`) may have its Wi-Fi connection closed by the system after it has been idle, and Apple's own key documentation for `UIRequiresPersistentWiFi` references a 30-minute idle closure for that specific app-network-activity case — this is not the same as "the phone leaves the Wi-Fi network," since the device typically remains associated for system-level traffic even when a given app's foreground network session is torn down.
    **Sources:** [Apple Developer — `UIRequiresPersistentWiFi`](https://developer.apple.com/documentation/bundleresources/information-property-list/uirequirespersistentwifi), [Apple Developer — `NEHotspotConfiguration.joinOnce`](https://developer.apple.com/documentation/networkextension/nehotspotconfiguration/joinonce) (documents a *different*, narrower case: a join-once hotspot profile disconnects on sleep or after the configuring app is backgrounded >15s — not representative of normal home-Wi-Fi association).
    **Support:** direct evidence, but it answers a narrower question (app network session / join-once hotspot) than "does the phone's radio detach from the home AP." The general-case idle/sleep disconnect timing for a phone's standing Wi-Fi association to a normal home network was **not found** in a primary Apple source during this pass. **Confidence:** low on the general claim; medium on the specific documented cases.

18. **Claim:** Android's Doze power-saving mode can restrict background network access when the screen is off and the device is stationary, but AOSP does not document a fixed Wi-Fi-radio disconnect timer either; actual disconnect/reassociation behavior is OEM- and device-specific and not standardized by the platform docs.
    **Sources:** [AOSP — Platform power management with Doze](https://source.android.com/docs/core/power/platform_mgmt).
    **Support:** direct evidence (absence of a documented fixed timer), consistent with practitioner reports (HA community threads, finding 9) of inconsistent/flapping presence signals for phones specifically.
    **Support:** direct evidence for "no fixed platform timer"; the practical consequence (how long a phone might look "away" via ARP/ping even while still associated) is researcher inference, not directly measured in a primary source.
    **Confidence:** medium.

19. **Claim:** Practitioner evidence (not a spec, but real-world reports) consistently shows that ARP/ping/nmap-style presence checks against phones are the least stable of the three methods — HA's own docs warn generically that phones "turn off WiFi when idle" making such simple trackers unreliable, and the nmap/HA threads above show real flapping on Android phones specifically, implying ARP replies or ICMP responses can silently fail even while the phone stays radio-associated to the AP (association ≠ guaranteed L3/L4 responsiveness).
    **Sources:** [HA Nmap Tracker docs](https://www.home-assistant.io/integrations/nmap_tracker/), [nmap/nmap#92](https://github.com/nmap/nmap/issues/92), [HA community thread](https://community.home-assistant.io/t/nmap-device-scanner-unstable-device-state/222015).
    **Support:** direct evidence (explicit warnings and bug reports) + researcher interpretation connecting cause (idle power save) to effect (missed probes). **Confidence:** medium-high.

## Contradictions
- None found between sources on the *mechanism* of DD-WRT's HTTP status pages vs. SSH tools — they are consistent (same underlying driver data, different transport).
- Possible tension, not a resolved contradiction: the DD-WRT info-disclosure advisory (finding 4) implies some older builds exposed `Info.live.htm` without authentication, while the current HA integration source always sends HTTP Basic Auth and treats 401 as a hard failure. This may reflect a historical vulnerability that was patched, a build-specific configuration, or simply that HA always authenticates regardless of whether the target build requires it — the two sources do not directly address the same DD-WRT version, so this is recorded as an open discrepancy rather than resolved.
- No contradiction found on MAC-randomization defaults, but note the nuance: Android's persistent-vs-non-persistent split (finding 15) is a conditional/time-based behavior, not a flat default, so casual claims like "Android MACs never change on a known network" are an oversimplification of the AOSP doc.

## Missing evidence
- Whether DD-WRT's SNMP daemon exposes a usable, consistently-populated wireless-client-association MIB across builds — not found in a primary DD-WRT source in this pass.
- A primary Apple source giving a general idle/sleep Wi-Fi-association timeout for a phone sitting on a normal home AP (as opposed to the app-level `UIRequiresPersistentWiFi` 30-minute case or the narrow `joinOnce` hotspot case). Likely does not exist as a single published number, since Apple treats this as opportunistic OS/radio power management rather than a documented contract.
- A primary AOSP/OEM source giving a concrete "radio associated but ARP/ping unresponsive for N minutes while asleep" duration for Android. Current evidence is indirect (Doze docs + practitioner bug reports), not a measured number from Google.
- Exact definition of the Fritz!Box TR-064 `active` host field (association-derived vs. ARP/DHCP-derived) — not confirmed from the official AVM `hostsSCPD.pdf` service description in this pass (only the API shape was confirmed).
- Real-world measured frequency of iOS "Rotate Wi-Fi Address" firing on a stable home network (Apple describes it as "random times" without a bound) — relevant to whether per-phone MAC identity can be assumed stable for weeks/months in a typical Oiko deployment.

## Implications for Oiko

- **Which method to poll, in priority order:** prefer the router's native **Wi-Fi association** signal when available (DD-WRT `wl`/`iw` via SSH, or OpenWrt `ubus call iwinfo assoclist`) — it is closest to "radio currently attached" and does not depend on the phone answering an L3/L4 probe. Treat the **ARP table / DHCP lease** view as a fallback or corroborating signal, not the primary one, since it depends on recent IP traffic and lease timers rather than live association. Avoid relying on generic ARP/ping/nmap sweeps as the *only* signal for phones specifically — multiple primary and practitioner sources (HA's own docs, nmap upstream bug reports, HA community threads) document real flapping/false-absence for idle phones with that approach; it is acceptable as a router-agnostic fallback when no native API is available, but should be paired with a debounce/hysteresis window.
- **Recommended departure delay:** because none of the primary sources gives a hard, universal "phone goes idle/unresponsive after N minutes" number — Apple only documents a 30-minute app-level Wi-Fi teardown and a narrow 15-second join-once hotspot case; Android only documents Doze policy, not a radio timer — Oiko should not rely on a single poll's "absent" result. A practical, conservative **debounce window of roughly 10–20 minutes** of consecutive "not seen" results (at a reasonable poll interval, e.g. every 1–2 minutes) before declaring a phone departed is a reasonable researcher-derived compromise: short enough to be useful for automations, long enough to absorb the known false-negative patterns from idle/power-save behavior and from ARP/ping-based detection flakiness reported in practice. This number is an inference, not a value asserted by any source, and should be tunable/configurable rather than hard-coded.
- **How to identify a phone:** use the **MAC address** as the primary stable key, not host name or IP. On a given, already-known home network, both iOS (Fixed mode, the default for secured networks) and Android (persistent randomization, the Android 10/11 default and still the common case in Android 12+) keep one randomized MAC per network for extended periods, so MAC-per-network is usable as a durable per-device identifier for Oiko's purposes — but it is explicitly **not** the device's real hardware MAC, will differ from the MAC the same phone presents on any other network, and can occasionally change on the *same* network (iOS 18+ opt-in rotation at unspecified times; Android 12+ non-persistent mode under specific lease/time conditions). IP address is unreliable as an identity key because DHCP can reassign it. Host name is unreliable because many phones don't send a DHCP hostname or send a generic/non-unique one, and nothing in the primary sources guarantees its presence or stability. Oiko's onboarding/pairing flow should therefore capture the MAC explicitly (e.g. during initial setup when the phone is known to be present) rather than trying to infer phone identity from name or IP alone, and should tolerate occasional MAC changes by allowing re-pairing rather than assuming permanence.
