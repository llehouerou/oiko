# Repository presentation and extension-author onboarding patterns in comparable Go/self-hosted projects

Ticket: https://github.com/llehouerou/oiko/issues/81

## Summary

Across Caddy, Home Assistant, Homebridge, Traefik, Zigbee2MQTT, and Immich, a recurring shape emerges: a short, visual README that pitches the project and immediately links out to a documentation *website* (not the README itself) for anything beyond a two-minute quick start; a separate, dedicated "extend/write-a-plugin" doc page paired with a **template/scaffold repository or generator command** that a developer clones or runs instead of reading prose first; a **lightweight, automatic or convention-based registry** (topic tag, package registry search, or in-core PR) rather than a manually curated list wherever possible; and support funneled to one or two channels (Discord/Forum/Discussions) kept separate from GitHub Issues, which are reserved for bugs/features. CONTRIBUTING and SECURITY are almost always separate top-level files, with SECURITY.md defining scope and a private-report path (GitHub Security Advisories), and CONTRIBUTING increasingly stating an explicit policy on LLM-generated contributions (Caddy, Immich). These patterns map cleanly onto Oiko's "Bridge = compiled-in Go package, indexed via `oiko-bridge.json` + GitHub topic" model, closest to Caddy's module/`xcaddy` approach and Traefik's plugin-catalog-by-topic approach.

## Findings

### 1. Caddy (`caddyserver/caddy`)

1. **Claim:** Caddy's README is short and highly visual (centered logo/picture, tagline "Every site on HTTPS", one-line pitch, badges, then a link row to Releases / Documentation / Get Help), followed by a Features bullet list, Install, Build-from-source, and a Quick-start section that explicitly redirects to the website rather than inlining a tutorial. **Sources:** [README.md](https://github.com/caddyserver/caddy/blob/master/README.md). **Support:** direct evidence. **Confidence:** high.
2. **Claim:** Caddy's extension story has three coordinated parts: the conceptual doc "Extending Caddy" on the docs site explaining the module system and distinguishing "Caddy modules" from plain Go modules; the build tool **xcaddy** (`caddyserver/xcaddy`) which compiles a custom binary with `xcaddy build --with github.com/org/plugin`; and a documented manual alternative (fork `main.go`, add blank imports, `go build`) for when you don't want the tool. **Sources:** [Extending Caddy](https://caddyserver.com/docs/extending-caddy), [xcaddy repo](https://github.com/caddyserver/xcaddy), [Caddy README build section](https://github.com/caddyserver/caddy/blob/master/README.md). **Support:** direct evidence. **Confidence:** high.
3. **Claim:** Caddy topics on GitHub are infrastructure/feature-oriented, not plugin-oriented: `acme, automatic-https, caddy, caddyfile, go, golang, http, http-server, http3, https, privacy, reverse-proxy, security, tls, web-server`. **Sources:** [github.com/caddyserver/caddy](https://github.com/caddyserver/caddy). **Support:** direct evidence. **Confidence:** high.
4. **Claim:** User and extension docs live entirely off-repo on `caddyserver.com/docs`, itself sourced from a separate `caddyserver/website` repo accepting community PRs; the README explicitly says "the docs are also open source" and links there for contributions to docs. **Sources:** [Welcome docs](https://caddyserver.com/docs/), [caddy README](https://github.com/caddyserver/caddy?tab=readme-ov-file). **Support:** direct evidence. **Confidence:** high.
5. **Claim:** CONTRIBUTING.md lives at `.github/CONTRIBUTING.md` and (per PR history) explicitly uses "module" terminology for plugins, points documentation contributions to the separate website repo, and discusses Go-modules/dependency policy. SECURITY.md lives at `.github/SECURITY.md`, defines a precise acceptable scope (bugs in Caddy's own source only; excludes misconfiguration, client-side issues, dependency CVEs), requires explicit disclosure of **any LLM use** in a report (with risk of "blocklisting" otherwise), and funnels reports to GitHub's private security-advisory form; no bug bounty is offered. **Sources:** [.github/CONTRIBUTING.md](https://github.com/caddyserver/caddy/blob/master/.github/CONTRIBUTING.md), [.github/SECURITY.md](https://github.com/caddyserver/caddy/blob/master/.github/SECURITY.md), [PR #3270](https://github.com/caddyserver/caddy/pull/3270). **Support:** direct evidence. **Confidence:** high.
6. **Claim:** Support is explicitly routed to a dedicated community forum (`caddy.community`, "Get Help" link in the README banner) rather than GitHub Discussions; Issues are implicitly reserved for bugs/features. **Sources:** [README.md](https://github.com/caddyserver/caddy/blob/master/README.md). **Support:** direct evidence. **Confidence:** high.

### 3. Homebridge (`homebridge/homebridge`, `homebridge/homebridge-plugin-template`, `developers.homebridge.io`)

### 4. Traefik (`traefik/traefik`, `traefik/plugindemo`, `plugins.traefik.io`)

1. **Claim:** Traefik's README structure is a textbook "pitch → feature bullets → supported backends → quickstart link → web UI screenshot → documentation link → support → release cycle → contributing → maintainers → mailing lists → credits" layout, anchored by a table-of-contents-style menu row near the top and framed by badges (docs, license, community-forum, Twitter). **Sources:** [README.md](https://github.com/traefik/traefik/blob/master/README.md). **Support:** direct evidence. **Confidence:** high.
2. **Claim:** GitHub topics on `traefik/traefik` are infra-oriented: `consul, docker, etcd, go, golang, kubernetes, letsencrypt, load-balancer, marathon, mesos, microservice, reverse-proxy, traefik, zookeeper` — no plugin-specific topic on the core repo itself (plugin discovery instead keys off a topic applied to *plugin* repos, see below). **Sources:** [traefik/traefik](https://github.com/traefik/traefik). **Support:** direct evidence. **Confidence:** high.
3. **Claim:** The extension-author path has four pieces: (a) a reference/demo repo `traefik/plugindemo` showing the exact Go API shape a middleware plugin must expose (`Config`, `CreateConfig()`, `New(ctx, next, config, name) (http.Handler, error)`); (b) `traefik/yaegi`, the embedded Go interpreter Traefik uses to execute plugins **without recompiling the Traefik binary**, which is the key architectural difference from Caddy/xcaddy; (c) a dedicated "Developing Traefik Plugins" doc page on `plugins.traefik.io/create`; (d) local-dev support via a `./plugins-local/src/<module-path>/` convention plus `experimental.localPlugins` config before publishing. **Sources:** [traefik/plugindemo](https://github.com/traefik/plugindemo), [traefik/yaegi](https://github.com/traefik/yaegi), [Developing Traefik Plugins](https://plugins.traefik.io/create). **Support:** direct evidence. **Confidence:** high.
4. **Claim:** The **Traefik Plugin Catalog** (`plugins.traefik.io`) is a fully automated registry: any public, non-fork GitHub repo that carries the GitHub topic `traefik-plugin`, a root `.traefik.yml` manifest with valid `testData`, a valid `go.mod`, vendored dependencies if needed, and a version Git tag is automatically discovered and listed — there is no manual submission/approval step described. This is the closest external analogue to Oiko's "index via manifest file + GitHub topic" design. **Sources:** [Developing Traefik Plugins](https://plugins.traefik.io/create), [Working with Traefik Plugins](https://plugins.traefik.io/install). **Support:** direct evidence. **Confidence:** high.

6. **Claim:** Support is explicitly split: community support via the Discourse-based `community.traefik.io` forum (badge-linked in the README); commercial support via a named email (`support@traefik.io`); security announcements and general announcements via separate Google Groups mailing lists (`security+subscribe@traefik.io`, `news+subscribe@traefik.io`). ## Contradictions

- **Plugin-loading architecture differs fundamentally between the two Go reverse-proxy peers.** Caddy requires **recompiling a custom binary** (via `xcaddy` or manual `go build`) to add a module/plugin, because modules are statically linked Go code — architecturally the same constraint Oiko has (ADR 0017: Bridges are compiled in). Traefik instead uses **Yaegi, an embedded Go interpreter**, to load plugin source *without* recompiling the main `traefik` binary. These are genuinely incompatible models for "how an extension gets into the running binary," and a reader should not treat "Traefik plugins" and "Caddy modules" as the same kind of thing when picking lessons for Oiko, whose architecture is explicitly the Caddy/xcaddy kind, not the Traefik/Yaegi kind. **Sources:** [Extending Caddy](https://caddyserver.com/docs/extending-caddy), [xcaddy](https://github.com/caddyserver/xcaddy), [Developing Traefik Plugins](https://plugins.traefik.io/create).
- **"Registry" means different things project to project**, and this is worth flagging rather than collapsing into one pattern: Traefik's catalog is a fully automated crawl keyed on a GitHub topic + manifest file (closest to Oiko's design); Homebridge's is a human-curated verification *overlay* on top of npm-registry discovery-by-keyword; Home Assistant's and Zigbee2MQTT's device/integration "registries" are really just their own core/converters repositories merging in contributions via normal PR review, with no separate catalogue at all. No contradiction in fact, but these are not interchangeable models.

## Patterns that fit Oiko

Given Oiko is a single Go binary (ADR 0017: Bridges are compiled in by `oiko-build`, catalogued via an `oiko-bridge.json` manifest + `oiko-bridge` GitHub topic), the two closest architectural analogues are **Caddy/xcaddy** (compiled-in modules) and **Traefik's Plugin Catalog** (manifest + topic → automatic discovery), with Home Assistant/Homebridge/Zigbee2MQTT contributing softer lessons about docs placement, scaffolding, and support-channel hygiene, and Immich contributing lessons about README i18n and an explicit AI-contribution policy.

1. **README as a short, visual lobby, not a manual.** Every project studied keeps the root README to a pitch, 1–2 images/badges, a feature list, and a link row out to Releases/Documentation/Get-Help — never an inline tutorial (Caddy, Traefik, Zigbee2MQTT, Immich all do this explicitly). Oiko's README should follow the same shape: pitch, maybe one screenshot of the web client, a short feature list, and links to `docs/`, releases, and wherever Discussions/chat ends up.
2. **One canonical "Extending Oiko" doc, modeled on Caddy's page, that explains the Bridge-as-compiled-Go-package model before any tutorial.** Caddy's "Extending Caddy" page first teaches the *concept* (modules vs. Go modules) before showing `xcaddy build`; Oiko should do the same for Bridges vs. ordinary Go packages, since the "compiled-in" constraint is the one thing new authors most need to understand up front (it differs from Traefik's and Homebridge's dynamically-loaded models, so Oiko can't borrow their "no rebuild needed" framing).
3. **A build tool analogous to `xcaddy`, if Oiko doesn't already have one as ergonomic as `oiko-build` promises.** `xcaddy build --with <module>` is the single biggest usability win for compiled-in-module projects; Oiko's own `oiko-build` (per ADR 0017) is already the right shape — the research gap is making sure its README/docs surface a one-liner as prominent as `xcaddy build --with ...`.
4. **A template repository (Homebridge-style) rather than only prose.** Homebridge's `homebridge-plugin-template` (a literal GitHub "template" repo, usable via the "Use this template" button) lowers the barrier more than a scaffold command tucked inside the core repo (Home Assistant's `script.scaffold`, which requires an existing dev checkout of core). For a compiled-in model like Oiko's, a small template Bridge repo (minimal Go package + `oiko-bridge.json` + example test) that a developer clones, renames, and registers is likely the best fit — closer to Homebridge's and Traefik's `plugindemo` than to Home Assistant's in-tree generator, since Oiko Bridges presumably live in their own repos to be discovered via the `oiko-bridge` topic (unlike HA integrations, which live inside core).
5. **Let the catalogue be mechanical, keyed on the manifest + topic, Traefik-style — not manually curated.** Traefik's Plugin Catalog auto-discovers any repo with the `traefik-plugin` topic, a `.traefik.yml`, and a `go.mod`; this is effectively the design ADR 0017/the ticket describes for Oiko already (`oiko-bridge.json` + `oiko-bridge` topic). The validated external lesson is to publish the **exact manifest schema and required fields** as prominently as Traefik does on `plugins.traefik.io/create`, and to make the catalogue's discovery criteria machine-checkable (so a Bridge author can verify eligibility without waiting on a maintainer), rather than drifting toward Homebridge's human-verification model (which adds a trust badge but also a review bottleneck) or Home Assistant's "merge into core" model (which isn't applicable since Oiko Bridges are external compiled-in packages, not vendored into the main tree).
6. **A safe, no-rebuild test path for new Bridge authors, if feasible — borrowing the *intent*, not the mechanism, of Zigbee2MQTT's external converters.** Zigbee2MQTT lets an author validate a new device definition via a sandboxed, explicitly-opt-in, locally-loaded file before it's merged upstream. Oiko's compiled-in model can't replicate "no rebuild" directly, but the same *intent* — "test your Bridge against a real running Oiko instance without going through the full catalogue/registration ceremony" — maps to documenting a local `oiko-build --with <local-path>` workflow (mirroring xcaddy's local-replace pattern) prominently in the extension docs, so authors don't have to publish/tag a release just to iterate.
7. **Keep CONTRIBUTING and SECURITY as separate root files, and state an explicit AI-contribution policy.** Every actively maintained project here (Caddy, Traefik, Home Assistant, Immich) keeps these as distinct top-level Markdown files rather than folded into the README, and the two most recently updated ones (Caddy's SECURITY.md, Immich's CONTRIBUTING.md) both now include explicit rules about LLM-assisted contributions/reports. Given AGENTS.md already governs Oiko's own repo conventions, Oiko should add (or confirm it has) a standalone `SECURITY.md` with a scoped report path (GitHub Security Advisories, as used by Caddy, Traefik, and Immich) and consider stating its stance on AI-generated Bridge PRs explicitly, following Immich's model of distinguishing "AI as a tool" from "AI as a ghostwriter for communication."
8. **Centralize support to one or two channels, separate from Issues.** All six projects separate "ask a question" (Discord/Forum/Discussions) from "report a bug/request a feature" (structured GitHub Issue templates), several with pinned megathreads for recurring topics (Immich) or structured device/feature-request YAML templates (Zigbee2MQTT, Immich). Oiko should pick one primary channel (GitHub Discussions is the lowest-overhead choice already native to GitHub, matching Zigbee2MQTT's and Immich's usage) and keep Issues templates narrow and structured.
9. **Put all user- and extension-facing docs on a real docs site/section, not the README.** Every project (Caddy, Traefik, Home Assistant, Zigbee2MQTT, Immich) treats the README purely as an entry point and keeps substantive docs (including the extension tutorial) in a dedicated docs tree/site. Oiko's `docs/` + ADR pattern already matches this; the actionable addition is a specific, prominent "Writing a Bridge" page analogous to Caddy's "Extending Caddy," cross-linked from the README the same way Caddy's "Documentation" link is placed right under the pitch.
10. **GitHub topics should describe the product, not the extension mechanism, on the *main* repo — the extension mechanism's topic (`oiko-bridge`) belongs on the *Bridge* repos.** Caddy's and Traefik's own topics describe what the core product is (web server, reverse proxy), not "plugin." The plugin/extension-specific topic (`traefik-plugin`) is applied to the satellite plugin repos, which is exactly Oiko's existing design (`oiko-bridge` topic on Bridge repos) — this review found no evidence that any studied project also tags its *core* repo with its own plugin-topic, so Oiko should keep that separation clean.
