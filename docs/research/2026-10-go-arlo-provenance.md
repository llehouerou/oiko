# go-arlo / pyaarlo provenance review

Ticket: https://github.com/llehouerou/oiko/issues/90

## Scope and method

- `go-arlo` read locally at `a local checkout of go-arlo` (files: `README.md`, `client.go`, `api.go`, `login.go`, `mqtt.go`, `modes.go`, `devices.go`, `library.go`, `media.go`, `session.go`, `docs/NOTES.md`).
- `pyaarlo` read on GitHub. The exact tag `v0.8.0.23` does not exist in `twrecked/pyaarlo`'s git tags (the tag series jumps `v0.8.0.22` → no `.23` tag), even though PyPI carries a `pyaarlo==0.8.0.23` release built from that line of history. `v0.8.0.22` (commit `6e8bf6d`) is the closest tagged commit and is what this review fetched from `raw.githubusercontent.com`; the PyPI metadata for `0.8.0.23` was also checked (license field, changelog) to confirm it carries the same license and the same "trusted browser" auth design as `.22`. Files read: `pyaarlo/backend.py`, `pyaarlo/location.py`, `pyaarlo/media.py`, `pyaarlo/camera.py`, `pyaarlo/device.py`, `pyaarlo/constant.py`.
- **Missing evidence flag:** the comparison below is against `v0.8.0.22`, not the exact `0.8.0.23` tag go-arlo's README names (no such git tag exists). Treated as the best available proxy; a byte-exact diff against the `0.8.0.23` sdist from PyPI was not performed in this pass.

## Summary

`go-arlo` is, in its overwhelming majority, an independently structured Go reimplementation: different module layout, a single flat `api`/`Client` design instead of pyaarlo's deep class hierarchy (`ArloBackEnd`, `ArloDevice`, `ArloCamera`, `ArloLocation`, `ArloMediaLibrary`, …), different concurrency model (goroutines/channels vs. Python threads/locks), a far smaller feature surface (README: "scope is deliberately small"), and its own naming and control flow throughout. Most of what matches between the two projects — endpoint paths, JSON field names, the auth call sequence, MQTT topic shapes — are facts about Arlo's real wire protocol that both libraries had to reproduce because that is what the Arlo cloud actually accepts, not pyaarlo's creative expression. However, a small number of specific items are not protocol facts and do look carried over from pyaarlo's own text rather than rediscovered independently: a verbatim user-agent string literal, comments that name pyaarlo's private Python method names, a paraphrase of a pyaarlo code comment, and one near-identical one-line string fixup. These are narrow but real, and `go-arlo`'s own documentation (`docs/NOTES.md`, a section titled "What pyaarlo does (verified in the source)") states outright that pyaarlo's source, not just independent traffic capture, was the source of some of these facts.

## Findings

1. **Claim:** `go-arlo`'s module/type structure is independently designed, not a transliteration of pyaarlo's class hierarchy. **Sources:** [go-arlo client.go, api.go, devices.go](https://github.com/llehouerou/go-arlo) vs [pyaarlo/backend.py](https://raw.githubusercontent.com/twrecked/pyaarlo/v0.8.0.22/pyaarlo/backend.py), [pyaarlo/camera.py](https://raw.githubusercontent.com/twrecked/pyaarlo/v0.8.0.22/pyaarlo/camera.py), [pyaarlo/device.py](https://raw.githubusercontent.com/twrecked/pyaarlo/v0.8.0.22/pyaarlo/device.py). **Support:** direct evidence. **Confidence:** high.
   pyaarlo models devices as a stateful class tree (`ArloDevice` → `ArloChildDevice` → `ArloCamera`/`ArloLocation`/…) with hundreds of lines of attribute callbacks, nightlight/spotlight/floodlight/ambient-sensor handling, a threaded media downloader, and a SSE-or-MQTT dual backend. `go-arlo` has none of this: `device` is a 7-field JSON struct (`devices.go`), there is no equivalent of `ArloCamera`'s callback/property system, no media downloader, no SSE path, no nightlight/spotlight/ambient-sensor code at all. The README states this explicitly: "Scope is deliberately small." This is researcher interpretation of a structural comparison, not a quote from either project.

2. **Claim:** The auth flow's three-call sequence is explicitly named after pyaarlo's internal methods in a `go-arlo` comment, showing the port was done by reading pyaarlo's source rather than purely by sniffing Arlo's wire traffic. **Sources:** [go-arlo login.go, lines 105-106](https://github.com/llehouerou/go-arlo/blob/main/login.go) vs [pyaarlo/backend.py `_auth`, `_validate`, `_pair_auth_code`](https://raw.githubusercontent.com/twrecked/pyaarlo/v0.8.0.22/pyaarlo/backend.py). **Support:** direct evidence (quoted). **Confidence:** high.
   - go-arlo: `// authenticate follows pyaarlo's ArloBackEnd._auth, _validate and _pair_auth_code.`
   - pyaarlo defines exactly `def _auth(self) -> AuthResult:`, `def _validate(self):`, `def _pair_auth_code(self):` on `class ArloBackEnd`.
   The three-step sequence itself (auth → validate → pair) is a fact about what Arlo's backend requires; naming pyaarlo's private methods in the comment is not required to express that fact and shows pyaarlo's source, not just its outputs, was consulted. The Go implementation of each step is otherwise written from scratch (no retry loop, no cloudscraper/curl_cffi session juggling, different error types, different control flow for the one-attempt-only policy `docs/NOTES.md` describes as a deliberate divergence from pyaarlo's 3x retry).

3. **Claim:** The MQTT client-ID comment in `go-arlo` is a close paraphrase of pyaarlo's own comment about the same fact, not an independently worded observation. **Sources:** [go-arlo mqtt.go, line 69](https://github.com/llehouerou/go-arlo/blob/main/mqtt.go) vs [pyaarlo/backend.py `_mqtt_main`](https://raw.githubusercontent.com/twrecked/pyaarlo/v0.8.0.22/pyaarlo/backend.py). **Support:** direct evidence (quoted). **Confidence:** medium-high.
   - go-arlo: `// pyaarlo: the last 10 digits must be random.` immediately above `ClientID: fmt.Sprintf("user_%s_%010d", userID, rand.IntN(1e10))`.
   - pyaarlo: `# Build a new client_id per login. The last 10 numbers seem to need to be random.` immediately above `self._event_client_id = f"user_{self._user_id}_" + "".join(str(random.randint(0, 9)) for _ in range(10))`.
   The underlying fact (Arlo's broker needs a random 10-digit suffix) could in principle be rediscovered by independent experimentation, but the wording ("the last 10 … must/need to be random") and its placement as a code comment next to the same string-formatting idiom read as derived from pyaarlo's comment, explicitly credited as such ("pyaarlo:").

4. **Claim:** `go-arlo`'s default user-agent constant is copied verbatim from one of pyaarlo's `USER_AGENTS` dictionary entries, with an explicit comment acknowledging the source. **Sources:** [go-arlo client.go, lines 17-18](https://github.com/llehouerou/go-arlo/blob/main/client.go) vs [pyaarlo/constant.py `USER_AGENTS["arlo"]`](https://raw.githubusercontent.com/twrecked/pyaarlo/v0.8.0.22/pyaarlo/constant.py). **Support:** direct evidence (quoted). **Confidence:** high.
   - go-arlo: `// pyaarlo's default ("arlo" in its USER_AGENTS).` / `userAgent = "(iPhone15,2 18_1_1) iOS Arlo 5.4.3"`.
   - pyaarlo: `"arlo": "(iPhone15,2 18_1_1) iOS Arlo 5.4.3",` inside `USER_AGENTS = {...}`.
   The string value itself is a fact (a real iOS app's HTTP user-agent header), but go-arlo's own comment states it was taken as "pyaarlo's default" rather than independently captured from the Arlo iOS app or from `go-arlo`'s own traffic dumps. This is the clearest case of a literal value lifted from pyaarlo's source text rather than rediscovered.

5. **Claim:** One data-fixup one-liner (`rtsp://` → `rtsps://`) is near-identical in both projects, flagged in `go-arlo`'s own comment as copying pyaarlo's behavior. **Sources:** [go-arlo stream.go, lines 54-55](https://github.com/llehouerou/go-arlo/blob/main/stream.go) vs [pyaarlo/camera.py `_get_stream_url`/`_start_stream`](https://raw.githubusercontent.com/twrecked/pyaarlo/v0.8.0.22/pyaarlo/camera.py). **Support:** direct evidence (quoted). **Confidence:** medium (the expression is trivial/obvious given the fact, so low on its own, but is explicitly flagged by the author as a copied behavior).
   - go-arlo: `// streamURL reads startStream's answer. Arlo names the RTSPS stream rtsp://; pyaarlo fixes it the same way.` followed by `strings.Replace(r.URL, "rtsp://", "rtsps://", 1)`.
   - pyaarlo: `self._stream_url = self._stream_url["url"].replace("rtsp://", "rtsps://")` (appears twice, in `_get_stream_url` and `_start_stream`).
   A one-line string substitution is a thin, largely unprotectable piece of expression on its own (there are few other ways to write "replace this prefix"), but the comment again shows pyaarlo's code, not just Arlo's wire behavior, was the reference point.

6. **Claim:** Header maps, endpoint paths, and JSON field names match between the two projects because both talk to the same real Arlo API, not because of copied prose. **Sources:** [go-arlo api.go `authHeaders`/`apiCall`](https://github.com/llehouerou/go-arlo/blob/main/api.go), [go-arlo devices.go](https://github.com/llehouerou/go-arlo/blob/main/devices.go), [go-arlo library.go](https://github.com/llehouerou/go-arlo/blob/main/library.go) vs [pyaarlo/constant.py](https://raw.githubusercontent.com/twrecked/pyaarlo/v0.8.0.22/pyaarlo/constant.py), [pyaarlo/backend.py `_auth_headers`/`_headers`](https://raw.githubusercontent.com/twrecked/pyaarlo/v0.8.0.22/pyaarlo/backend.py). **Support:** interpretation. **Confidence:** medium.
   Both projects send the identical header set (`X-Service-Version: 3`, `X-User-Device-Automation-Name: QlJPV1NFUg==` — base64 of the literal string `BROWSER` — `X-User-Device-Type: BROWSER`, `Auth-Version: 2`, `SchemaVersion: 1`) and hit the identical paths (`/api/auth`, `/api/startAuth`, `/api/finishAuth`, `/api/getFactorId`, `/api/getFactors`, `/api/validateAccessToken`, `/api/startPairingFactor`, `/hmsweb/users/session/v3`, `/hmsweb/v2/users/devices`, `/hmsweb/automation/v3/activeMode`, `/hmsweb/users/library`, `/hmsweb/users/devices/notify/`, `/hmsweb/users/devices/startStream`, `/hmsweb/users/devices/fullFrameSnapshot`) and JSON keys (`deviceId`, `utcCreatedDate`, `mediaDurationSecond`, `contentType`, `reason`, `objCategory`, `presignedContentUrl`, `presignedThumbnailUrl`, `presignedLastImageUrl`, `presignedFullFrameSnapshotUrl`, `xCloudId`, `allowedMqttTopics`, `mqttUrl`). Under U.S. copyright doctrine, facts and the "facts" of an external protocol (what bytes a server will accept) are generally not themselves protectable, and a server that only accepts one exact set of header names/paths/JSON keys has little room for alternative "expression" of those facts (merger). `go-arlo`'s own `docs/NOTES.md` states some of this was independently "observed" (dumped HTTP responses), while other parts are explicitly cross-checked against pyaarlo ("What pyaarlo does (verified in the source)"), so the facts plausibly have two independent sources converging on the same required values.

7. **Claim:** The business logic built around those facts is written independently, with different behavior in several places that `docs/NOTES.md` calls out as deliberate divergence from pyaarlo. **Sources:** [go-arlo docs/NOTES.md, lines 33-44](https://github.com/llehouerou/go-arlo/blob/main/docs/NOTES.md). **Support:** direct evidence (quoted). **Confidence:** high.
   - `"One auth attempt per command, never an automatic retry (pyaarlo retries 3x)."`
   - `"On start, validate the saved token (/api/validateAccessToken) and only call /api/auth when it is expired or rejected. pyaarlo always re-authenticates."`
   This shows the author read pyaarlo's behavior closely enough to describe and then intentionally change it, which is more consistent with "independent implementation informed by a competitor's documented behavior" than wholesale transcription.

## Contradictions

- `go-arlo`'s README and package comment say it is "ported from pyaarlo 0.8.0.23," which on its face suggests a close, possibly line-level port; the actual code, however, shows a largely independent Go structure with only a handful of passages that look textually derived from pyaarlo. The word "ported" is broader than what the code shows — it is accurate for the protocol knowledge and the general approach, but could be read by a licensing reviewer as implying more code-level derivation than is actually present. No contradicting evidence found about the license fields themselves: `pyaarlo`'s PyPI metadata for both `0.8.0.22`-line commits and the `0.8.0.23` release both report `License: LGPLv3+`/`GNU Lesser General Public License v3 or later (LGPLv3+)`, consistent with the ticket's premise.

## Missing evidence

- No git tag `v0.8.0.23` exists in `twrecked/pyaarlo`; the comparison used `v0.8.0.22` as the closest available source and the PyPI `0.8.0.23` README/metadata for confirmation of license and high-level behavior. A full diff of the exact `0.8.0.23` sdist (`pyaarlo-0.8.0.23.tar.gz` on PyPI) against `go-arlo`'s current `main` was not performed; given `.22`→`.23` is a point release, material differences in the compared modules are unlikely but not proven.
- `source_check` was not invoked for this task; no registered provider confirmation beyond direct manual reading and quoting of both source trees was obtained. The provenance conclusions above rest on direct reading of both repositories by this researcher, not on a separate automated corroboration pass.
- Whether a "port … informed by reading the source" of an LGPL library, with the specific overlaps found in findings 2–5, legally rises to "derivative work" status under copyright law is an open legal question this report does not resolve (see "Conclusions" below, which separates fact from legal advice).
- Not reviewed: `go-arlo`'s `cmd/arlo/*.go`, `events.go`, `run_test.go`, `fake_test.go`, `imap.go`, and pyaarlo's `main.py`, `base.py`, `cfg.py`, `tfa.py`, `sseclient.py`, `super.py`. These were skipped as lower-risk (CLI wiring, tests, and pyaarlo's CLI/auth-helper/SSE code with no close `go-arlo` analog observed in the files that were reviewed). A full-repo pass would reduce residual risk further.

## Conclusions (facts vs. interpretation; not legal advice)

**What looks like protocol facts, independently expressed:** The large majority of `go-arlo` — its module layout, concurrency model (goroutines/channels vs. Python threads), type system, the shape of its public API (`Client`, `Event` types, `Config`), and the specific business logic around retries, token validation timing, and backoff — is original Go expression built on top of facts about Arlo's real wire protocol (endpoint paths, JSON field names, HTTP headers, the three-step auth handshake, the MQTT topic/credential shape). These facts are necessarily shared with pyaarlo because both talk to the same non-public, reverse-engineered API; under general copyright principles, facts and the narrow "correct" expression of a required protocol are not themselves protectable (this is an interpretation of general copyright doctrine, not a citation to a specific ruling about this code).

**What looks derived from pyaarlo's expression rather than its facts:** (a) the literal `USER_AGENTS["arlo"]` user-agent string, copied verbatim and explicitly credited as "pyaarlo's default"; (b) comments that name pyaarlo's private method names (`ArloBackEnd._auth`, `_validate`, `_pair_auth_code`) and that paraphrase pyaarlo's own code comment about the MQTT client-ID's random suffix; (c) the matching one-line `rtsp://`→`rtsps://` fixup, flagged in `go-arlo`'s own comment as "pyaarlo fixes it the same way." These are small in code volume but are not reducible to "the only way to express this fact" — they are specific wording and a specific data value that `go-arlo` itself attributes to having come from reading pyaarlo's source, not from independent traffic capture.

**Whether `go-arlo` can plausibly keep MIT as-is:** This is a judgment call this report does not make as legal advice. Two honest readings exist:
- *Narrow-derivation reading:* the handful of items above are minor (a few words of comment, one constant, one trivial one-liner) relative to the whole codebase, and could be removed or independently re-derived without materially changing the project, so the bulk of `go-arlo` is a clean MIT-appropriate reimplementation once those specific items are fixed.
- *Derivative-work-risk reading:* because `go-arlo`'s own documentation states the auth/MQTT logic was built by reading and consciously tracking pyaarlo's method-level behavior (not solely from independent wire capture), a copyright holder could argue the auth and MQTT modules as a whole are an adaptation of pyaarlo's organization of that behavior, which would need to honor LGPL-3.0-or-later, regardless of how much of the literal text differs.

**What would have to change, under either reading, to reduce risk:**
1. Remove or rewrite the items in findings 2–5: drop the comments naming pyaarlo's private methods, reword the MQTT client-ID comment to describe the requirement in `go-arlo`'s own words (or cite it as an Arlo-side fact observed in `go-arlo`'s own dumps, per `docs/NOTES.md`'s existing practice), and source the user-agent string independently (e.g., from `go-arlo`'s own capture of the real iOS Arlo app's header, consistent with how `docs/NOTES.md` already documents "observed" behavior) rather than from pyaarlo's constant.
2. Add an attribution/NOTICE entry crediting pyaarlo/`twrecked` for the protocol knowledge the port relied on, regardless of the licensing outcome — this is good practice and reduces risk either way, and the README already names pyaarlo as the source, which should be preserved and made more precise (e.g., state "protocol behavior cross-checked against pyaarlo 0.8.0.22/0.8.0.23" rather than "ported from," if the maintainer wants the wording to match what the code actually does).
3. If the maintainer prefers not to do the rewrite in (1), the more conservative option is to relicense `go-arlo` itself as LGPL-3.0-or-later (or dual-license MIT/LGPL for the parts that are genuinely independent, LGPL for the auth/MQTT module if kept as-is), with a copy of the LGPL/GPL license texts and attribution to pyaarlo. LGPL is compatible with being used from a differently-licensed program (unlike plain GPL), so this would not force the rest of Oiko to become LGPL, but it changes what `oiko-arlo`/Oiko must do when distributing a binary (see next section).

**What an Oiko build that includes `oiko-arlo` would then owe to pyaarlo, if `go-arlo`'s auth/MQTT code is treated as LGPL-3.0-or-later-encumbered:** (again, not legal advice, offered as the practical shape of the obligation)
- LGPLv3 §4 ("Combined Works") permits linking (static or dynamic) an LGPL library into a differently-licensed program, provided the distributor either (a) distributes the combined work under terms that let a recipient modify the LGPL portions and relink a modified version with the application's object code ("Minimal Corresponding Source" + "Corresponding Application Code"), or (b) uses a shared-library mechanism that lets the user substitute a modified library at runtime. For a statically linked Go binary, route (a) is the realistic one.
- Because Oiko's own repository is already fully public source (per this repo's own `AGENTS.md`: "This repo is public"), the Corresponding Source condition is largely already satisfied in spirit; what would still need attention is: including the LGPLv3 and GPLv3 license texts in the distributed artifact/docs, a clear, prominent notice that `oiko-arlo` links LGPL-3.0-or-later code from (a derivative of) pyaarlo, and explicit confirmation/documentation that a user can rebuild `oiko-arlo` against a modified `go-arlo` using the published build (which, for a standard `go build`, is normally true already, but should be stated rather than assumed).
- If instead `go-arlo` is cleaned up per item 1 above and MIT is kept, Oiko owes pyaarlo nothing beyond the existing README attribution, since no LGPL-covered expression would remain.
